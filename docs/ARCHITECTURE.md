# SAFAR — Architecture

> The Living Journey Network — *Every Person. Every Moment. One Intelligent Journey.*

SAFAR is a two-service monorepo: a FastAPI/SQLAlchemy API and a Next.js App Router
frontend. Every recommendation is produced by deterministic, inspectable Python
services; nothing is generated by an external model. The product rule is enforced
everywhere: **the engine recommends, the group decides.**

---

## 1. System overview

Two clients share this API: the Next.js web app below and the Flutter mobile
app in `apps/mobile` (architecture in §2.1). Neither client holds business
rules, authorisation checks or AI inference.

weather, link metadata, OCR, translation, LLM, email and storage states.

### 2.1 Flutter client (`apps/mobile`)

```
apps/mobile/lib/
  app/            GoRouter (auth gate, StatefulShellRoute bottom bar), root
  core/
    config/       compile-time API base URL (no production localhost default)
    network/      Dio, auth interceptor, SafarCookieJar, ApiException
    storage/      JsonStore abstraction (secure storage / in-memory tests)
    models/       typed immutable models with explicit fromJson
    repositories/ per-domain transport only
    theme/        SAFAR tokens + Material 3 light/dark
    widgets/      shared primitives and states
  features/       auth · home · discover · trips · trip · assistant · profile
```

- **State**: Riverpod 2.6 (`StateNotifier` session controller,
  `FutureProvider.family` reads, invalidation after mutations).
- **Auth**: native persists only the cookie jar (Keychain on iOS, encrypted
  preferences on Android); access and CSRF tokens are memory-only. Web
  verification uses `withCredentials` so the browser owns the HttpOnly cookies.
  A 401 triggers one single-flight refresh, token rotation and one retry; a
  rejected refresh signs the user out. Logout revokes the session server-side.
- **Boundary**: the Dart layer ranks nothing, extracts nothing, forecasts
  nothing and filters no privacy data. It submits requests and renders labels,
  sources and confidence exactly as the API returns them.
- **Realtime**: one ticket-authenticated WebSocket per open trip
  (`POST /api/auth/ws-ticket` → `/ws/trips/{id}?token=`), with exponential
  backoff, event dedupe, lifecycle pause/resume and a catch-up invalidation on
  reconnect. Membership events invalidate both the member and invitation reads,
  so role changes and removals appear without a manual refresh. Pull-to-refresh
  and post-mutation refresh remain the fallback.
- **Maps**: `MapTileConfig.fromEnvironment()` reads a tile template at compile
  time (`SAFAR_MAP_TILE_URL` with `{z}`/`{x}`/`{y}`, attribution, subdomains,
  zoom range). Release builds reject non-HTTPS tile URLs and invalid templates;
  with no configuration the Nearby screen renders a labelled schematic map.
  Precise origin requires the profile's location-sharing consent before the OS
  permission is requested, and coordinates are used only for the current query.
- **Android release**: the main manifest disables cleartext and backups; debug
  only overlays cleartext for local development. Release signing is resolved
  from environment variables (or an untracked `key.properties`) and the build
  fails rather than fall back to the debug key.
- **Platforms**: Android and iOS are the primary targets. Android debug,
  release APK and AAB builds are verified in Phase 10; iOS requires a macOS
  host. A Flutter web build remains a visual verification target only.
- Migration status, test evidence and remaining gaps:
  `docs/FLUTTER_MIGRATION_PLAN.md` §8 and §9.

```

                               sessions, RLS)
  scripts/retention.py         scheduled retention entry point
  tests/                       pytest (SQLite by default, PostgreSQL via
                               SAFAR_TEST_DATABASE_URL)

```

### Authorization model

* Sessions are server-side. Login creates an `auth_sessions` row and sets an
  HttpOnly access cookie (15 minutes) and an HttpOnly refresh cookie (30 days,
  path `/api/auth`), plus a readable CSRF cookie. Refresh tokens are opaque,
  stored only as SHA-256 hashes and rotated on every use. Bearer tokens are
  still accepted for API clients.
* `get_current_user` verifies the JWT, rejects inactive/deleted users, checks
  that the backing session is still active, and enforces CSRF for cookie-based
  unsafe methods. `get_trip_and_member` loads the trip and the caller's active
  membership; `require_role(owner|admin)` gates mutations that rewrite
  confirmed plans.
* Private fields are filtered in serializers, not only in the UI:
  member budget limits and access need details are returned only for the
  viewer's own membership; pact `individual_limits` are returned per-member;
  private memories are filtered by visibility rules in every read path
  (timeline, replay, travel book, offline snapshot).
* PostgreSQL Row Level Security is the database backstop. All 55 model tables
  use `ENABLE` + `FORCE ROW LEVEL SECURITY` with 220 policies and 35
  `SECURITY DEFINER` helpers. Each transaction receives its identity through
  transaction-local GUCs (`app.user_id`, `app.admin`, `app.system`,
  `app.auth`, `app.companion_link`, `app.invitation_token`); the runtime role
  is a non-owner without `BYPASSRLS`. Application-layer checks remain for
  precise error semantics, but a missing filter cannot leak rows.

## 4. Intelligence layer (deterministic, explainable)

The prompt forbids routing everything through one LLM. SAFAR instead implements
separate services, each with explicit inputs and labelled outputs:

| Capability | Module | Behaviour |
|---|---|---|
| Personal preference model | `services/dna.py`, `services/feedback.py` | DNA scores 0–10, explicit edits; feedback updates only with consent + personalisation consent |
| Destination recommender | `services/ranking.py`, `services/discovery.py` | tag/fit scoring, lens (balanced/iconic/similar), freshness labels |
| Group recommendation model | `services/engine.py` (Everyone Wins / Your Turn / Surprise Us) | hard constraints filter first (budget, access, time, radius, protected time), fairness metrics, per-activity explanation, grounded place respect guidance, bounded consent-gated feedback nudge, diversity-aware selection, batch evaluation metrics (`meta.evaluation`); engine `1.5` |
| Journey optimiser | `services/engine.py`, `services/rescue.py`, `services/impact.py` | alternative-day comparison, rescue recovery, cost impact |
| Day scheduling | `services/schedule.py` | shared free-window/conflict calculation (08:00–22:00 day window), protected blocks, overlap detection used by the engine, itinerary edits, proposal approval, twin and rescue |
| Traveller matching | `services/discovery.py` (serendipity) | opt-in, reciprocal, heuristic overlap |
| Place intelligence | `services/places.py` | provenance, freshness, access chain, crowd forecast v2 (MAD outlier filter, 120-day age cap, hierarchical fallback, 80% interval, separate observed/predicted blocks), reports |
| Memory intelligence | `services/memory.py` | session grouping + grounded caption drafts requiring approval |
| Dream Import | `services/discovery.py` | structural extraction with source spans and review; optional SSRF-guarded link metadata; local-only OCR for uploaded images |
| Conversational AI | `services/assistant.py`, `services/language.py` | eight-language detection and localised templates, multilingual intent lexicons, per-request context pack, citations and provenance; no external model |

All outputs carry explicit labels: `VERIFIED` / `REPORTED` / `ESTIMATED` /
`PREDICTED` / `UNKNOWN`, freshness ages, and uncertainty notes. The assistant
advertises `external_llm: false`, `translation: true` (local templates) and
whether a weather provider is configured, and explains any limitation in the
answer itself. Optional providers are server-side only; keys never reach the
browser and `/api/ai/capabilities` returns states without credentials.

### Hard-constraint semantics

Ranking is filter-then-score. A member's hard budget limit, declared
accessibility needs, available time and travel radius remove activities before
scoring. Protected itinerary blocks (`is_protected`) are reserved time: the
engine only considers candidates that fit the remaining free windows and fails
with `422` when none exist, and add/PATCH, proposal approval, twin adoption and
rescue return `409` rather than overlap or remove one. A proposal that would
break the Journey Pact or a member's hard budget limit is rejected at approval
time with `409`. Private values are used as filters but never returned to other
members.

## 5. Data model

55 model tables (56 relations with `alembic_version`), grouped by domain:

* **Identity & consent** — users, profiles, journey_dna, consent_records,
  auth_sessions, user_blocks, notifications, audit_logs, activity_feedback
* **Trips** — trips, trip_members, trip_invitations, journey_pacts,
  planner_tasks, trip_branches, material_watch, journey_capsules,
  trip_missions, user_missions
* **Catalog** — destinations, places, activities, place_sources, place_reports
* **Planning** — itineraries, itinerary_items, itinerary_versions,
  itinerary_proposals, itinerary_approvals, activity_votes,
  itinerary_attendance, shadowplans
* **Intelligence** — recommendation_batches, recommendations,
  recommendation_feedback, activity_feedback
* **Pulse & ground** — trip_pulse, ground_requests, ground_responses
* **Money** — expenses, expense_participants, expense_settlements
* **Memory** — trip_memories, memory_events, memory_permissions (media files
  live on disk; only the signed URL is stored in `trip_memories.media_url`)
* **Social** — travel_circles, circle_members, circle_posts,
  local_contributors, traveller_matches, connection_requests,
  saved_inspiration, abuse_reports
* **Offline** — offline_sync_queue (client-generated ids; replaying the same
  entry returns the stored status instead of creating duplicates, and a reused
  client id with different content is rejected)
* **Companion** — companion_links (signed, scoped, single-use links) and
  companion_responses (value + optional comment only; no user id, IP or user
  agent is stored)

Coordinates are stored as `lat`/`lon` floats and distances use the haversine
formula. PostgreSQL is plain 16.x: no PostGIS or other extension is used.

Migrations: `services/api/migrations` (Alembic; baseline `9c224ee10414`,
companion links `b1f6c2d84e71`, server-side sessions `c7d3e9a1f204`, row-level
security `d9e4f1b2c305`). Development and SQLite tests use `create_all`;
PostgreSQL tests and production use `alembic upgrade head`. There are no
SQLite-only schema features: JSON columns, foreign keys and indexes are
portable, and the RLS migration is a no-op on SQLite.

## 6. Real time

`core/realtime.py` keeps an in-process connection manager. Clients request a
short-lived ticket with `POST /api/auth/ws-ticket` and connect to
`/ws/trips/{trip_id}?token=…`; the ticket is a two-minute JWT with
`typ: ws`, bound to the caller's session, and membership is re-checked before
acceptance. The first-party client always uses this ticket; for compatibility
the socket endpoint also accepts a normal access token. The handshake cannot
carry an `Authorization` header, so the token is in the query string: TLS and
proxy query-string log redaction are deployment requirements (see
`docs/SECURITY.md` §7). Writers (proposals,
votes, itinerary changes, expenses, memories, pulse updates) publish events;
`lib/realtime.ts` invalidates the matching TanStack Query keys, so open
screens refresh without polling.

The websocket only broadcasts identifiers and event names — never private
member data — and all reads still pass through the HTTP authorization layer
and RLS.

## 7. Trust, privacy and honesty invariants

* No confirmed itinerary is modified by an engine, rescue, twin or branch; all
  changes become proposals requiring owner/admin approval.
* No live member locations are stored or exposed; meeting points are explicit
  trip fields.
* Community observations remain `REPORTED` until a moderator verifies a source;
  a single report never becomes `VERIFIED`.
* Crowd forecasts and travel times are labelled predictions/estimates; when the
  data is insufficient the UI says so and shows the latest observation instead.
  Forecasts return observed and predicted blocks separately, reject outliers and
  stale reports, and state the granularity used.
* The assistant never invents facts; it cites recorded trip data and states
  missing providers (weather, live availability), unsupported languages and
  mixed-language input. Answers never execute a change; consequential actions
  are proposal links with `requires_approval`.
* Optional providers (weather, link metadata, OCR) are off or local by default,
  are disclosed through a key-free capability endpoint, and never receive a
  user identifier, message, preference or budget.
* Error and empty states are explicit everywhere; there is no fake data path.

## 8. Deployment topology

```
browser ──HTTPS──▶ reverse proxy ──▶ web (Next.js, :3000)
                                └──▶ api (:8000) ──▶ PostgreSQL 16
                                          └──▶ /app/storage (signed media)
```

`docker-compose.yml` builds both images, runs `alembic upgrade head` before the
API starts, seeds only when `SAFAR_SEED=true` (off by default in the compose
production profile), runs both containers as unprivileged users and gates
startup on `/api/ready`. Media is a named volume; production object storage is
not configured — the upload path validates size, declared type and magic bytes
and writes to local disk.

Logging is structured JSON on stdout with request ids, redacted token paths
and hashed client IPs. Uvicorn's raw access log is disabled. Error monitoring
has an integration point (`sentry-sdk` + `SENTRY_DSN`, no PII) but no paid
provider is required or configured. Rate limiting is per-process. See
`docs/DEPLOYMENT.md` for backup/restore, retention and scaling limits.

## 9. Observability & Operational Reliability Architecture

### Backend Monitoring & Structured Telemetry
* **Structured JSON Logging:** Emitted across specialized loggers (`safar.access`, `safar.error`, `safar.auth`, `safar.security`, `safar.db`, `safar.alert`, `safar.sync`, `safar.media`, `safar.ws`).
* **Sensitive-Data Redaction:** Redacts companion/invitation/media tokens in paths, query strings (`?token=...`, `?sig=...`, `?key=...`), authorization headers, cookies, passwords, private memories, and precise coordinates.
* **Request Correlation:** Outermost `RequestContextMiddleware` generates or extracts `X-Request-Id`, binds it to `request_id_var` ContextVar, and returns it in every response and error payload.
* **Operational Metrics Collector (`MetricsCollector`):** In-memory thread-safe collector tracking HTTP status codes, latencies, security/auth events, database queries and slow queries, WebSocket connections, media uploads, and offline sync.
* **Admin Observability Endpoint:** `GET /api/admin/metrics` secured via `require_admin` dependency; exposes real operational telemetry, database connection pool statistics, latency, media disk usage, and backup status.
* **Alerting Abstraction (`AlertManager`):** Debounced operational alerts with cooldown (5 minutes default) for critical conditions (DB down, auth spikes, token reuse, 5xx error spikes, backup failure); logs to `safar.alert` with optional webhook integration.

### Flutter Application Observability
* **Global Error Boundaries:** `FlutterError.onError` and `PlatformDispatcher.instance.onError` capture uncaught framework and asynchronous zone errors into `DiagnosticsService`.
* **In-Memory Circular Buffer:** `DiagnosticsService` keeps recent telemetry (max 100 entries) with strict redaction of sensitive credentials, tokens, and private memories.
* **Network & WebSocket Diagnostics:** `ApiClient` and `TripChannel` record durations, status codes, socket state transitions (`connecting`, `live`, `reconnecting`, `closed`), and reconnection backoffs.
* **Offline Synchronization State Tracking:** `OfflineQueue` tracks `pending`, `syncing`, and `failed` item states with retry count and error diagnostics, preserving data across app restarts with user-initiated recovery.

```
            │                                                   │
            │                         ┌─────────────────────────┼─────────────────────────┐
            │                         │                         │                         │
            ▼                         ▼                         ▼                         ▼
    [ Public APIs ]        [ Distributed Cache ]     [ Private Object Storage ]   [ PostgreSQL 17 + PostGIS ]
    (HTTPS/WSS)            (Redis Cluster / ElastiCache)  (AWS S3 / Cloudflare R2)  (Supabase Pro / AWS RDS)
                           - Shared Rate Limits      - Encrypted Media Files      - Multi-AZ Deployment
                           - Session Invalidation    - Presigned URLs (12h TTL)   - Continuous WAL Archiving
                           - WebSocket Pub/Sub Bus                                - Automated PITR (RPO <15m)
```

### Production Components & Scaling Plan
1. **API Tier:** FastAPI running under Uvicorn/Gunicorn across multi-container autoscaling clusters (AWS ECS Fargate or Google Cloud Run). Health/readiness checks wired to ALB target groups.
2. **Database Tier:** Managed PostgreSQL 17 (Supabase Pro or AWS RDS) with PgBouncer connection pooling, enforced Row-Level Security, non-owner `safar_app` execution role, and automated continuous WAL archiving providing Point-in-Time Recovery (PITR) with RPO < 15 min and RTO < 1 hour.
3. **Caching & Coordination:** Redis cluster for distributed sliding-window rate limiting (auth, companion, uploads), WebSocket pub/sub message dissemination across API instances, and revoked session blacklists.
4. **Object Storage:** Private AWS S3 or Cloudflare R2 bucket with client-side magic-byte sniffing and server-generated expiring presigned URLs (12-hour TTL), replacing local filesystem storage.
5. **Frontend Tier:** Next.js 15.5 App Router deployed to Vercel or containerized on Cloud Run with global edge caching.
6. **Mobile Distribution:** Official production Android App Bundle signed with Google Play App Signing upload key; iOS release IPA compiled on macOS via Xcode 15+ and distributed via TestFlight and App Store.
